Featured work

Three selected parts of my work on Birds of Impalitism.

01 / Featured work

Deciding what the save file owns

The save needed to remember more than a checkpoint. Player position, pickups, progression, and world flags had to agree after loading, even when different systems produced those values.

I designed a shared data model and a save controller that gathers state from the battery tracker, goggle chunks, and world flags. Each scene tracks its own progression so reloading one area does not overwrite another.

02 / Featured work

Keeping progression through scene changes

A player should not lose a collected item or a dialogue step just because they leave an area. The difficult part was keeping scene-local objects and shared progression from disagreeing after a transition.

Subsystems report their state to the unified save file at checkpoints and exits. When a scene loads, it reads the relevant data before presenting its objects, so each area can restore its own progress.

03 / Featured work

Rebuilding the world on load

A save file is only useful if the loaded world matches it. I added an automatic load path that reconstructs object and world state when a scene opens, with validation for invalid entries before they can cause errors.

That work is mostly invisible during normal play, but it lets a player resume without finding an already-collected item back in the world or an unlocked area closed again.

Supporting contributions

  • Dialogue interaction logic
  • Checkpoint and scene-exit save triggers
  • Player stat persistence
  • Invalid-save validation
  • Design documentation for subsystem owners

Project takeaway

Birds of Impalitism made state ownership a concrete design concern for me. The visible result is simply a world that remembers the player, but getting there required every scene and subsystem to agree on what the save file means.
